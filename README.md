# japango: AI が書いた日本語を、中身を変えずに人が書いた文へ直す

AI に書かせた記事・報告・エッセイなどの日本語を、そのジャンルを読み慣れた人が「人が書いた」と感じる文に直すためのスキルです。事実・主張・条件・書き手の調子は変えません。Claude Code（プラグイン）と Codex（スキル）で使えます。

ライセンスは MIT です。

## 何をするか

AI に「自然に直して」と頼むと、直すべき文を見落とすか、全文を書き直して原文に無い原因や数字を足すことがよくあります。japango は、見つけることと直すことを分け、直す段を機械にします。

1. **文に ID を振る**（`japango.py ids`）: 原稿を段落と文に分け、`[p2-s3]` のような ID を付けます。ID から原文に戻せることを毎回確かめます
2. **見つける**: 別の目で読む「見つける役」が、型の一覧（`references/rubric.md`）に照らして、文ごとに「削る／言い換える／書き手に聞く／残す」を決めた指摘一覧を書きます。言い換える文には、そのまま置ける完成した文を付けます。その会話で書いた原稿なら書き手自身の 1 回と別の目の 1 回、外から来た原稿ならサブエージェントで 2 回、独立に走らせます（サブエージェントを使えないツールでは同じ会話で 1 回）
3. **まとめる**（`japango.py merge`）: 外から来た原稿では、削る・言い換えるは 2 回が一致した文だけを採ります。書き手自身の回と別の目を合わせるときは、どちらかが直すと言った文を採ります。どちらの場合も、片方が「残す」と言った文は残します。呼び名や動詞をそろえる言い換えで、回ごとにそろえ先の語が違う文は、どちらも採らずに確認欄で聞きます
4. **組み立てる**（`japango.py assemble`）: 指摘を機械で原文に当てます。言い換えた文に、原文のどこにも無い原因・限定・時間の語（だけ・ため・まで など）や数字が入っていたら、その文は原文に戻します。書き手に聞く文には `〔確認1〕` の印を付け、問いを末尾の確認欄にまとめます。削った文にしか出ない語を後の文が「両課」「この方式」のように受けている箇所と、削って 1 文だけ残った段落も、確認欄の末尾に出します（自動では直しません）
5. **読み直す**: 組み立てた本文を「読者役」（`references/reader.md`）が想定読者として通して読み、文末の単調さと時制の合わない所だけを指摘し、その指摘をもう一度まとめて組み立てます（1 回目の確認欄はそのまま残り、問いはその続きに足されます）

指摘一覧に無い文は、構造上だれも触れません。

## 入れ方

### Claude Code

```
/plugin marketplace add og3-lab/japango
/plugin install japango@japango
```

### Codex

Codex は、作業するリポジトリの `.agents/skills/` の下に置いたスキルを読みます。このリポジトリの `skills/japango/` フォルダを中身ごと、`.agents/skills/japango/` にコピーしてください。

```bash
# 作業するリポジトリの直下で実行
git clone --depth 1 https://github.com/og3-lab/japango /tmp/japango
mkdir -p .agents/skills
cp -R /tmp/japango/skills/japango .agents/skills/japango
```

### 要るもの

Python 3.8 以上か Node.js 18 以上の、どちらか 1 つが入っていれば動きます。スクリプトは同じ中身のものを両方入れてあり（`japango.py` と `japango.mjs`。どちらも標準の機能だけで動きます）、AI が動く方を選びます。どちらで動かしたかは最後の報告に出ます。出てくるものは、どちらで動かしても一字一句同じです。

どちらも入っていなければ、japango は止まって入れ方を案内します（自分では入れません）。

- Windows: Node.js をおすすめします（`winget install OpenJS.NodeJS.LTS`、または [nodejs.org](https://nodejs.org/) のインストーラー）。Windows の Codex では、ふつうの入れ方で入れた Python（`%LOCALAPPDATA%\Programs\Python` の下）を、作業環境（サンドボックス）が起動させないことがあるためです
- Mac: `brew install node`、または nodejs.org のインストーラー
- Linux: たいてい `python3` が入っています

入れた後は、Claude Code や Codex を開き直してから頼んでください。

## 使い方

直したいファイルを示して、名前を出して頼みます。

```
japango で report.md を直して
```

文章をそのまま貼って「japango で直して」と頼むこともできます。

出てくるもの:

| ファイル | 中身 |
|---|---|
| `<原稿の名前>.japango.md` | 直した本文。末尾に確認欄（書き手に聞く問い）。同じ名前があれば `<原稿の名前>.japango-2.md` のように番号が付きます。原稿のファイルは書き換えません |
| `<原稿の名前>.japango/log.json` | 変えた文と残した文の前後（`changes`）、原文に戻した文と理由の語（`reverted`）、確認欄（`confirm`）、削った文が指していた語（`dangling`）、言い直しとして削った文にしか無い語（`lost`）、1 文だけ残った段落（`orphans`） |
| `<原稿の名前>.japango/` のほかのファイル | 文の一覧、ID つきの原稿、見つける役の書き出し（`notes1.md`）と指摘一覧（`findings1.jsonl`）、まとめた指摘 |

確認欄の問い（「誰が判断したか」「根拠は何か」など）は、原文に事実が無いため直せなかった文です。答えを足してもう一度頼むと、その事実を使って直せます。

スクリプトだけを手で使うこともできます（Node なら `python ...japango.py` を `node ...japango.mjs` に替えます）。

```
python skills/japango/scripts/japango.py ids draft.md work
# work/draft.annotated.txt を見つける役に読ませ、work/notes1.md に書き出し、work/findings1.jsonl に指摘を書かせる
python skills/japango/scripts/japango.py merge work/draft.units.jsonl work/merged.jsonl agree work/findings1.jsonl work/findings2.jsonl
python skills/japango/scripts/japango.py assemble work/draft.units.jsonl work/merged.jsonl work/log.json
# draft.md の横に draft.japango.md ができる（別の場所に書くときは --out パス）
```

## 試験の結果

見つける役は Claude Opus をサブエージェントとして動かし、採点は別の会話の Claude Sonnet が、どの方式かを伏せた出力を正解表と照らして行いました。点は「直すべき箇所」をいくつ直したか、違反は「守るべき箇所」を壊した数です。

### 調整に使っていない素材での結果（今の版）

japango の物差しの調整に使っていない 3 本（社内報告・解説記事・体験記。直すべき箇所 19、守るべき箇所 16。`evals/4-比較用/`）で、外から来た原稿の工程（見つける役 2 回の一致）を 3 回走らせました。確認欄で正しく聞いた箇所も直ったとみなしています。

| 直すべき箇所の点（/19、3 回） | 迷いやすい箇所（/9） | 守るべき箇所の違反 | 足した事実 |
|---|---|---|---|
| 19・19・19 | 9・9・9 | 1・1・0 | 0 |

違反 2 件は、どちらも「結論を先に書くと」のような前置きの扱いで、採点でも判断が分かれた箇所です。

### 組み方の比較

- その会話で書いた原稿 6 本（正解表 25 か所）で、書き手の会話のまま 1 回＋別の目 1 回を比べました。和でまとめると見落とし 0・壊した文 1、一致だけでは見落とし 6、書き手 1 回だけでは見落とし 2・壊した文 2 でした。書き手は自分の意図と照らせるので食い違いを拾い、直しすぎは別の目の「残す」が止めます
- 和で入った悪い言い換え 3 件は、どれも片方の回だけが出した言い換えでした。今は、そうした言い換えに確認の問いを付けます

### 文体とジャンル

だ・である調の技術メモ、くだけた話し言葉のブログ、取引先への敬語のメール、手順書、4000 字近い報告書の 5 本で、文末の内訳を前後で数えました。です・ます調の文が無い 3 本に、です・ます調の文は 1 つも入りませんでした。敬語のメールは敬語のまま、手順書は「〜する。」のままです。直しの多くは文ごとの削除で、言い換えは見つける役の文案をそのまま置くので、言い換えた文以外の文体は変わりません。

## 制限
- 測った原稿はどれも 1 本 600〜4500 字です。本 1 冊のような長さは試していません
- 採点役は各原稿 1 体です
- 1 回の推敲で、見つける役 2 回分（原稿 3 本でおよそ 10 万トークン）がかかります
- 足した事実の検査は、決まった語（原因・限定・時間）と数字だけを見ます。原文に無い名詞・動作（文を分けたときに足した「入れて使えます」など）や、言い換えで意味がずれた文は拾えません。原文にある語で指す先を決め直した言い換え（「同じ画面」を「予約と同じ Slack の画面」に、「前の処理／次の処理」を「集計の処理／送信の処理」にするなど）も、語はどれも原文にあるので通ります。片方の回だけの言い換えには確認の問いが付きますが、最後は人が原文と読み比べてください
- 直すのは文の単位までです。段落の組み直しや、構成の入れ替えはしません
- コードブロック・表・HTML の中は直しません。1 段落の中で改行して書いた文章（折り返しの改行）は、行ごとに区切ります
- 見つける役の判断は回ごとにぶれます。2 回走らせても、両方が同じ間違いをすれば防げません
