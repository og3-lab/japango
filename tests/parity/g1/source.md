# ログ転送バッチのリトライ設計についてのメモ

## 背景

夜間のログ転送バッチが、月に二、三回の頻度で途中停止している。原因は転送先ストレージの一時的な応答遅延で、タイムアウト後に例外が上位まで伝わり、バッチ全体が異常終了する。停止したバッチは翌朝に手動で再実行しているが、担当者の負担が無視できない量になってきた。

現代のシステム開発において、障害を前提とした設計はもはや避けて通れない課題である。

## 現状の問題点

現行の実装には次の三つの問題がある。

1. 転送処理にリトライが一切ない。一度の失敗でバッチが止まる。
2. 転送単位が日付ごとの一括で、途中まで成功していても最初からやり直しになる。
3. 失敗時のログに対象ファイル名が出ないため、どこで止まったかを追うのに時間がかかる。

特に二つ目が厄介だ。再実行のたびに数十ギガバイトを送り直しており、再実行そのものが二時間近くかかる。つまり、一度の小さな失敗が、大きな手戻りにつながっているということだ。

## 方針

リトライは指数バックオフで実装する。初回の待ち時間を二秒とし、失敗のたびに倍にして最大五回まで試す。待ち時間には0〜1秒のゆらぎを加え、複数のワーカーが同時に再送して転送先に負荷をかけるのを避ける。

転送単位はファイルごとに分割する。各ファイルの転送が終わった時点で完了記録を管理テーブルに書き込み、再実行時は未完了のファイルだけを対象にする。これにより、再実行の所要時間は失敗したファイル数に比例する程度に抑えられる見込みだ。

この二つを組み合わせることで、バッチの安定性は飛躍的に向上すると言っても過言ではない。

リトライ対象とする例外は、タイムアウトと接続断に限る。認証エラーや権限エラーは何度試しても結果が変わらないため、即座に失敗として扱い、通知を出す。何でもリトライすればよいというものではない。

## ログの改善

失敗時のログには、対象ファイル名、試行回数、例外の種類、待ち時間を必ず出力する。最終的に諦めた場合は、未完了のファイル一覧を一行ずつ出す。これで翌朝の調査が数分で済むはずだ。

## 残課題

- 管理テーブルの肥大化への対策（古い記録を三十日で削除する案を検討中）
- 転送先の容量不足を事前に検知する仕組み
- リトライ回数と待ち時間の値が妥当かどうかの検証

最後の点は、本番に近い環境で一週間ほど動かして判断する。

いずれにせよ、地道な改善の積み重ねこそが、信頼されるシステムを支える礎となるのである。
