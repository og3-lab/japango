# japango

AI が書いた日本語を、中身を変えずに直す手順です。規則（どの文をどう直すか）はこのファイルに書かず、`references/rubric.md`（型の一覧）と `references/finder.md`（見つける役の指示）に置いています。このファイルは工程と出すものだけを決めます。

以下、`<skill>` はこのスキルのフォルダ（この SKILL.md があるフォルダ）、`<原稿>` は直す文章のファイルです。

## スクリプトの動かし方
スクリプトは同じ中身のものが 2 つあります。`scripts/japango.py`（Python 3.8 以上）と `scripts/japango.mjs`（Node.js 18 以上）で、どちらも標準の機能だけで動き、同じ引数で同じファイルを書きます（テストで一字一句の一致を確かめている）。以下の `japango` は、次の順で最初に動いたものです。

1. `python <skill>/scripts/japango.py`（`python` が通らなければ `py -3`、`python3` の順に試す。Windows で見つからなければ `%LOCALAPPDATA%\Programs\Python\Python3*\python.exe` も探す）
2. Node.js: `node <skill>/scripts/japango.mjs`

「動いた」は、`--version` が通るだけでなく、手順 1 の ids が実際に起動して結果を出したことを言います（ツールの作業環境によっては、Python が見えても起動を拒まれる）。Python が拒まれたら Node に切り替え、以降の手順も同じ方で通します。

どちらも動かなければ、ここで止めて利用者に案内します。**自分で Python や Node を入れない**（PC の変更になる）。案内では、どちらか 1 つ入れればよいことと、次の入れ方を示します。
- Windows: Node.js を勧める（`winget install OpenJS.NodeJS.LTS`、または nodejs.org のインストーラー）。利用者ごとに入れた Python は、ツールの作業環境から起動を拒まれることがあるため
- Mac: `brew install node`、または nodejs.org のインストーラー
- Linux: まず `python3 --version` を確かめる（多くは入っている）。無ければ OS のパッケージで python3 か nodejs を入れる
- 入れた後は、Claude Code や Codex を開き直してから、もう一度頼んでもらう（開き直すまで新しいコマンドが見えないことがある）

**スクリプトを別の言語で書き直したり、手作業で代わりをしたりしない**（足した事実の検査や組み立ての決まりが、書き直した側では保たれない）。

## 0. 原稿と作業フォルダを決める
- ファイルを渡されたら、それが `<原稿>`。文章を貼られたら、作業フォルダに `input.md` として保存し、それを `<原稿>` にする
- 作業フォルダ `<作業>` は `<原稿>` と同じ場所の `<原稿の名前>.japango/`。一時ファイルはすべてこの中に作る（同じ場所でほかの作業が同時に動いても混ざらないように）
- 原稿のジャンル（記事・報告・メール・エッセイなど）と想定読者を、原稿か依頼から 1 行で決めておく。分からなければ原稿から推して進め、最後の報告に書く

## 1. 文に ID を振る

```
japango ids <原稿> <作業>
```

- `<作業>/<名前>.units.jsonl`（文の一覧）、`<名前>.annotated.txt`（`[p2-s3] 文` の形。見つける役が読む）、`<名前>.orig.md`（文の一覧から組み直した原文）ができる
- 出力の `round_trip` が `ok` であることを確かめる。`DIFF` なら（区切り方が原稿の書き方に合っていない）ここで止め、利用者にその旨を伝える
- コードブロック・表・HTML は区切らず、見つける役にも見せない（そのまま残る）

## 2. 見つける役に指摘一覧を書かせる
見つける役は、`references/finder.md` と `references/rubric.md` を読み、`<名前>.annotated.txt` を読んで、次の 2 つのファイルをこの順に書く。

- 書き出し（`<作業>/notes1.md`、2 回目は `notes2.md`）: finder.md の「書き出してから照らす」7 項目（名詞句・文末・否定の形・言い直し／締め／食い違い／作った事実・指示語と形式名詞・文の途中のかっこ・同じ助詞の重なり）
- 指摘一覧（`<作業>/findings1.jsonl`、2 回目は `findings2.jsonl`）: 1 件 1 行の JSON `{id, pattern, quote, effect, route, fix}`

route は delete（削る）／rewrite（言い換える。fix に完成した文）／ask（書き手に聞く。fix に問いだけ）／keep（残す）。

走らせ方は、原稿の出どころとツールで 3 通りに分ける（2026-10 の試験で、正解表 25 件に対し、自分＋別の目を和でまとめると見落とし 0、同じ 2 回を一致だけでまとめると見落とし 6、自分 1 回だけだと直さなくてよい文を壊す例があった）。

- **① この会話で書いた原稿（書き手の会話がある）**: 自分で 1 回＋別の目で 1 回。自分の回は、この会話のまま `finder.md` と `rubric.md` を読み、`<作業>/notes1.md`（書き出し）を先に書き終えてから `<作業>/findings1.jsonl` を書く。書き手は自分の意図と照らせるので、食い違いを拾いやすい。別の目の回はサブエージェントに任せ、下の②と同じものを渡して `notes2.md`・`findings2.jsonl` に書かせる。自分の回の結果は見せない。手順 3 は `union` でまとめる
- **② 外から来た原稿（書き手の会話が無い）で、サブエージェントを使えるツール**: 別の役として 2 回、独立に走らせる（並べて同時に起こしてよい）。それぞれに次を渡す: 2 つの references のパス、`<名前>.annotated.txt` のパス、ジャンルと想定読者、書き出し先（1 回目は `<作業>/notes1.md` と `<作業>/findings1.jsonl`、2 回目は `<作業>/notes2.md` と `<作業>/findings2.jsonl`）、「一時ファイルは `<作業>` の中に作る」こと。互いの結果は見せない。サブエージェントの種類とモデルは問わず、ファイルを読み書きできる汎用の役でよい（重いモデルほど見落としが減る）。手順 3 は `agree` でまとめる
- **③ サブエージェントを使えないツール**: 同じ会話で 1 回だけ行う。自分で `finder.md` と `rubric.md` を読み、その手順どおりに書く。このとき、感想や直し方など、ここまでの会話で原稿について先に考えたことに引きずられないよう、**`<作業>/notes1.md`（書き出し）を先に書き終えてから** `<作業>/findings1.jsonl`（指摘一覧）を書く。書き出しを省かない
- 見つける役に原稿を書き換えさせない。文案は fix の欄にだけ書かせる

## 3. 指摘をまとめる

```
japango merge <作業>/<名前>.units.jsonl <作業>/merged.jsonl <agree|union> <作業>/findings1.jsonl [<作業>/findings2.jsonl]
```

- `agree`（②で使う）: 削る・言い換えるは、2 回ともその文を直すと言ったときだけ採る。どちらかが keep なら残す（keep の行として merged に残り、集計の `keep` に数えられる）。聞く（ask）は 2 回の和。1 回だけのとき（③）は、その 1 回の指摘がそのまま採られる
- `union`（①で使う）: どちらか 1 回が直すと言えば採る。どちらかが keep なら残すのは同じで、自分の回の直しすぎを別の目の keep が止める。片方の回だけが出した言い換えは採ったうえで、確認欄に「原文に無い行動・出来事が増えていないか」を聞く（試験では、和で入った悪い直し 3 件がすべてこの形だった）。②で利用者が「強めに」と頼んだときにも使う
- 期限や今後の予定だけを聞く問いは落ちる。文まるごとの太字・1 文に 2 か所以上の太字は、どちらの回も触れていなければ機械で外す
- 出力の `warnings` に ID の無い行・種類の不明な行が出たら、その回の書き出しを確かめる

## 4. 組み立てる

```
japango assemble <作業>/<名前>.units.jsonl <作業>/merged.jsonl <作業>/log.json
```

- 直した本文は、スクリプトが `<原稿>` と同じフォルダの `<原稿の名前>.japango.md` に直接書く。同じ名前があれば `<原稿の名前>.japango-2.md` のように番号を付け、原稿そのものは書き換えない。書いた先は出力の `out` に出る（手で写さない）
- 直す役は通さない。削る・聞くは機械が当て、言い換えは見つける役の fix の文をそのまま置く
- 言い換えた文に、原文全体のどこにも無い原因・限定・時間の語（だけ・のみ・ため・により・原因・まで・以降 など）や数字が入っていれば、その文は原文に戻る（`log.json` の `reverted`）
- 聞く文には本文の文の後ろに `〔確認n〕` の印が付き、問いは本文の末尾の「確認欄」にまとまる。削った文への問いは、その前に残っている文に印が付く。番号は本文に出てくる順で、同じ問いは 1 つにまとまる。1 つの文に問いが 2 つ以上あれば、1 つの印の下に問いを 1 行ずつ並べる
- 削った文にしか出ない語（漢字・カタカナ 2 字以上）を、残った後の文が「両課」「この方式」「同社」「前述の〜」のように受けていれば、`log.json` の `dangling` に記録し、確認欄の末尾に「削った文が指していた語が残っていません: …」と出す
- 削った結果 1 文だけになった段落（箇条書き・見出し・引用・表・コードは除く。本文が 1 段落だけになったときも除く）は、`log.json` の `orphans` に記録し、確認欄の末尾に「1 文だけ残った段落: 〔…〕」と出す
- この 2 つは自動では直さない（戻さない・つながない）。数は組み立ての出力の `dangling` と `orphans` に出る
- `〔確認n〕` の印は、文の句点（とそれに続く閉じかっこ・太字の印）の直後に置く。印と次の文の間は原稿のまま（空白があれば空白、無ければ詰めたまま）で、行末の空白（改行の印）より前に入る
- keep にした文は本文を変えず、`log.json` の `changes` に `"result": "残した"` で記録される（変えた文は `"result": "変えた"`）

## 5. 利用者に示す
次を示して終える。

1. 直した本文のファイルのパス（組み立ての出力の `out`。短い原稿なら本文も）
2. 確認欄の問い（`〔確認n〕` とその問い）。書き手が答えれば、その事実を足して直せる
3. 原文に戻した文（`log.json` の `reverted`）と、戻した理由の語
4. 確認欄の末尾の「削った文が指していた語が残っていません」「1 文だけ残った段落」（`log.json` の `dangling` と `orphans`）。あれば、直すかどうかは利用者に任せる
5. 変えた文の数と残した文の数（組み立ての出力の `changed` と `kept`。中身は `log.json` の `changes`）と、見つける役を何回走らせたか（2 回か 1 回か）、スクリプトを Python と Node のどちらで動かしたか
6. 0 で決めたジャンルと想定読者を推して決めたときは、そのこと

「本文だけ」と頼まれても、確認欄と `log.json` はファイルに残す。

## してはいけないこと
- 指摘一覧に無い文を直さない。組み立ての後に手で本文を書き足さない（足した事実の検査を通らなくなる）
- 原稿のファイルを上書きしない
- 確認欄の問いに、自分で答えを推して埋めない
